Claude 的记忆系统：显著性、做梦，和 MEMORY.md 的前 200 行

发表于2026-11-16|更新于2026-11-16|AI
|浏览量:

Anthropic 十一月初发了一篇讲智能体记忆的文章，说了一件挺根本的事：Claude 要从经验里学习，就必须在不知道未来会发生什么的时候，先决定什么值得记住。全文翻译放在这里（双语对照，带原文全部引用链接）。

这篇不重复原文内容，只写我自己的三个收获和一个联想。都是我看完之后过了几天还留在脑子里的东西。

先说结论

记忆系统的第一性问题不是”怎么存”，是”该记什么“。存的能力（文件夹、数据库、检索）早就过剩了，判断力才是稀缺的——判断哪些东西值得从日志里捞出来变成知识。整篇文章的所有实验，本质上都在测这个判断力。

1. 记什么，比怎么记重要：413 个文件输给 9 个

文章里最狠的一组对比：让两个模型玩宝可梦，各自管自己的记忆文件夹。

  • Sonnet 3.7：什么都存，每场战斗、每件道具、每个 NPC 一个文件——225 个文件夹、413 个文件，拿了 1 枚徽章。到后期它一半的步数花在整理记忆而不是玩游戏上。
  • Fable 5：只存游戏没告诉它的东西——战术、计划、验证过的规则——9 个文件，4 枚徽章。

关键区别不是勤奋，是取舍。玩家有多少钱、站在地图哪里，屏幕上随时读得到，存下来就是负资产：会过时、要维护、还会把真正重要的东西淹没掉。Fable 5 那条”连续三个精灵球失败就改变投球节奏”的笔记，才是屏幕上读不到、不写下来就会消失的知识。

写代码注释和文档的时候，我经常想起这 413 个文件——把代码里一眼能读出来的东西复述进注释里，就是 Sonnet 3.7 干的事。

2. 做梦：有时间回望，才有资格向前

会话内当场写记忆，本质是在不知道未来需要什么的时候做预测，所以一定会错。文章里 Claude 在月见山把宝可梦中心的位置记错了，之后一路信任这条错误笔记，三次摔下同一个悬崖。

解法是**做梦（dreaming，Claude 的真实机制，不是比喻）：空闲时拿记忆笔记对照会话日志逐条校验**，日志是 ground truth，对不上的笔记改掉。听起来朴素，但工程含义很实在——原始日志别急着删、别无脑压缩，它是记忆唯一能对账的凭据。所有”帮 AI 总结经验”的系统，缺了这份对账凭据就是在给错误笔记盖章。

3. MEMORY.md 的前 200 行：我天天在用的记忆层级

文章里记忆分四层：日志 → 笔记 → 表示（wiki）→ 注入上下文。最顶上那层要求极小——注入的 token 是真金白银，一条错笔记会污染每一个新会话，而且指令越长模型越不听话。所以 Claude Code 的 auto memory 只把 MEMORY.md 的前 200 行装进上下文，充当索引：知道有什么、去哪找，细节留在下面几层。

这套东西我天天在用——这个博客的写作流程就跑在 Claude Code 上。上周我们为了一篇翻译文吵了一整天：tag 怎么打、要不要从首页隐藏、阅读模式长什么样。吵完的约定，第二天全躺在它的记忆文件里了；这周再说”翻一篇新的”，它直接按规矩走，一次都没再问。文章里那套四层记忆，落地到我这儿就是那 200 行索引加几个约定文件。

4. 表示的价值在抽象：别造比帝国还大的地图

不是所有任务都值得建知识表示。测试里，需要跨文档找信息、要用判断力的任务，wiki 把成绩从 73% 拉到 87%；而单文档搜索就能命中的任务，wiki 毫无增益——甚至有一次 wiki 长到了 203KB，比 115KB 的原文档还大。文章引了博尔赫斯那个制图师的寓言：画了一张和帝国一样大的地图，等于什么也没抽象。

这让我想起五月写的 LLM Wiki 与 Agent 知识层——有意思的是，原文里”wiki”这个词引用的正是 Karpathy 那篇方法论（我们当时参考的是中文转述，这次算是接上了源头）。两篇合起来读，结论一致：知识层的价值在于压缩，不在于收录。 建表示之前先问一句：它比搜索省了多少次翻找？省不出来的，就是那张 1:1 的地图。

收尾

文章留了两个开放问题，我觉得也是做工程时最实际的两问：记忆该当场写还是离线写（当场写分散注意力，离线写不够即时），以及怎么保鲜（环境变了，记忆会从资产变成毒药，全量校验又太贵）。

对照着看自己手头的系统——不管是给 AI 建的还是给人建的——大部分问题都能归到这两问上。
